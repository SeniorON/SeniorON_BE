# SOS 주소 후처리

`POST /api/event/sos`는 위도·경도로 이벤트와 알림을 저장한 뒤 FCM 발송을 전용 작업 풀에 맡기고 즉시 응답한다.
카카오 역지오코딩은 DB 커밋 후 별도 작업 풀에서 실행하며, SOS 응답은 주소 조회와 FCM 발송 결과를 기다리지 않는다.
롤백된 이벤트에는 주소 조회 작업이 실행되지 않는다.

- 최초 SOS 응답의 `address`는 `주소 확인 중`이다. `latitude`, `longitude`는 즉시 사용할 수 있다.
- 주소 조회 완료 후 `GET /api/event/{eventId}`에서 갱신된 주소를 확인할 수 있다.
  앱은 좌표로 지도를 먼저 표시하고, 주소가 확인 중인 경우 상세를 다시 조회해야 한다.
  이미 받은 SOS 응답이 자동으로 바뀌거나 주소 갱신 푸시가 추가로 발송되지는 않는다.
- 주소 조회 실패 시 안내 문구를 저장하며 좌표와 SOS 이벤트는 유지한다.
- 외부 호출 중에는 DB 트랜잭션을 열지 않고, 주소 UPDATE만 별도 트랜잭션으로 처리한다.

주소 작업 풀은 SOS 발송 풀과 분리하며 최대 2개 작업을 동시에 실행하고 100개를 대기시킨다.
큐 포화 시 요청 스레드에서 대신 주소를 조회하지 않고 경고 로그를 남긴다.
현재 작업 큐는 메모리에 있으므로 서버 강제 종료·큐 포화·DB 갱신 실패 시 주소가 `주소 확인 중`으로 남을 수 있다.
주소 작업의 영속 저장이나 자동 재시도(아웃박스)는 포함하지 않는다.

카카오 주소 클라이언트에는 연결 1초, 읽기 2초 타임아웃을 적용한다.
이 클라이언트를 공유하는 무활동·외출/귀가 주소 조회에도 적용되며, 해당 API의 동기 조회 구조는 유지한다.
이 값의 합은 DNS 등 모든 단계를 포함하는 엄격한 전체 호출 시간 상한을 의미하지 않는다.

`SOS 주소 조회 소요시간=...ms, eventId=...` 로그로 외부 조회 시간을 확인할 수 있다.
API 지연 개선 폭은 배포 후 같은 부하와 측정 구간으로 평균 및 P95를 비교한다.

## SOS 발송 적체 제어

SOS 발송 풀은 동시 실행 8개, 대기 큐 100개로 제한한다. 큐 포화 시 요청 스레드에서
대신 발송하지 않고 작업을 거부하며 API 응답은 정상적으로 반환한다.
`notification.sos.max-queue-wait-ms`는 기기별 작업의 최대 대기시간이며 기본값은 30000ms다.
이는 운영 초기값으로, 실제 요청량과 FCM 지연을 보고 조정한다.
만료된 미실행 작업은 큐에서 제거하고 발송하지 않는다. 이미 실행 중인 FCM 호출은
이 대기시간 제한으로 취소하지 않으며 실제 접수 성공·실패로 집계한다.
기존 5초 결과 강제 실패 처리는 제거했다. 실행 중인 호출이 지연되면 결과 집계도 지연된다.

- `sos_device_dispatch_total{result="rejected"}`: 큐 포화 또는 executor 종료로 등록 거부
- `sos_device_dispatch_total{result="expired"}`: 최대 대기시간 초과로 미발송
- `sos_device_dispatch_total{result="cancelled"}`: 종료 과정에서 대기 작업 취소
- `sos_dispatch_total`: 기존 수신자별 성공/부분 성공/미발송 집계 유지
- `fcm_send_total`: 실제 FCM 호출 결과 유지

위 메트릭과 오류 로그는 애플리케이션에서 기록한다. 운영 알림 규칙은 별도 모니터링 시스템에서 설정한다.
서버 강제 종료 시 인메모리 발송 작업 유실 가능성은 유지되며 자동 재시도는 하지 않는다.
