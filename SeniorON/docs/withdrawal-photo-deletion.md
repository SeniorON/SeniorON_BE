# 탈퇴 시 가족사진 삭제

## 처리 흐름

계정의 현재 역할과 관계없이 본인이 업로드한 가족사진, 공유 대상, 열람 기록을 탈퇴 트랜잭션에서 삭제한다. 신고 이력은 유지하며, 신고 검토를 위해 이미 별도 보존했던 원본 키도 정리 대상에 포함한다.

삭제할 S3 키는 같은 트랜잭션의 `s3_deletion_task` 테이블에 저장한다. 탈퇴가 롤백되면 사진 데이터와 삭제 작업도 함께 롤백된다. 요청 스레드는 S3 삭제를 기다리지 않는다.

스케줄러가 커밋된 작업을 최대 1,000건씩 읽고 S3 `DeleteObjects`로 삭제한다. 성공한 작업만 제거하며, 객체별 실패와 요청 전체 실패는 작업에 사유와 횟수를 기록한다. 실패 시 재시도 간격은 1분부터 늘어나 최대 1시간이며 횟수 제한 없이 재시도한다. 서버 종료로 처리 결과를 커밋하지 못하면 작업은 DB에 남아 다시 처리된다. 이미 없는 S3 키의 재삭제는 성공으로 취급된다. API의 일괄 삭제 제한과 객체별 결과 처리는 [AWS DeleteObjects 문서](https://docs.aws.amazon.com/AmazonS3/latest/API/API_DeleteObjects.html)를 따른다.

작업자는 전용 실행 스레드에서 S3를 호출하므로 공용 스케줄러의 다른 예약 작업을 막지 않는다. S3 호출 중 삭제 작업 행만 잠그며, 계정이나 사진 행은 잠그지 않는다. 작업자 트랜잭션은 `READ_COMMITTED`를 사용하여 범위 조회의 gap lock이 새 삭제 작업 등록을 막지 않도록 한다. 여러 인스턴스가 같은 작업을 동시에 처리하지 않도록 한다. 배치의 API 호출 제한 시간은 30초다.

## 배포 및 운영

- Flyway `V20261116_02__create_s3_deletion_task.sql`을 적용한다. Flyway를 끄는 로컬 프로필에서는 JPA가 스키마를 생성한다.
- `S3_DELETION_ENABLED`: 기본 `true`.
- `S3_DELETION_INITIAL_DELAY_MS`: 시작 후 첫 실행까지 지연, 기본 `30000`.
- `S3_DELETION_FIXED_DELAY_MS`: 작업 제출 시도 사이의 간격, 기본 `30000`. 이전 배치가 아직 실행 중이면 다음 주기에서 다시 시도한다.
- `attempt_count`, `last_error`, `next_attempt_at`으로 실패 원인과 재시도 일정을 확인한다. 권한 오류 등 지속 실패는 원인을 수정해야 한다.
- 탈퇴 응답은 DB 삭제 및 삭제 작업 저장 완료를 뜻한다. S3 파일 삭제는 이후 스케줄에서 완료되므로 응답 시점에 즉시 삭제된다고 가정하지 않는다.
- 일반 사진 삭제의 기존 처리 방식과 기존 탈퇴 계정의 일괄 정리는 이번 변경 범위에 포함하지 않는다.

## 관리자 프론트 연동

관리자 사진 신고 상세의 `photo.imageUrl`과 게시자 신고 상세의 `reportedPhoto.imageUrl`은 게시자가 없거나 탈퇴한 경우 `null`이다. 신고 이력과 집계는 계속 제공한다.

프론트는 URL이 있을 때만 이미지와 원본 보기 링크를 렌더링하고, `null`이면 사진을 확인할 수 없다는 대체 문구를 표시해야 한다. 사진 레코드 삭제 여부를 나타내는 `deleted`와 URL 존재 여부는 각각 판단한다. URL을 문자열로 강제 변환하거나 `<img src="null">`로 렌더링하지 않는다.
